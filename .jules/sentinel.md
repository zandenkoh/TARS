## 2026-04-01 - SSRF Vulnerability in Discord Attachment Download
**Vulnerability:** The Discord channel implementation in `TARS/channels/discord.py` downloaded file attachments from user messages without validating the URL against SSRF using `validate_url_target`.
**Learning:** Even though Discord attachment URLs are generally from Discord's CDN, depending on how Discord Gateway provides it or if an attacker manipulates the payload, it could potentially inject a malicious URL, leading to SSRF.
**Prevention:** Always validate all external URLs, including those originating from external service APIs like Discord, using `validate_url_target` before downloading or interacting with them via HTTP clients.

## 2026-04-01 - SSRF Vulnerability in DingTalk Media Download
**Vulnerability:** The DingTalk channel implementation in `TARS/channels/dingtalk.py` blindly fetched files from a user-supplied URL (`downloadUrl` from the API) via `httpx.get(..., follow_redirects=True)` without validating the domain or IP target.
**Learning:** Even if the URL originally comes from an API response (like DingTalk's `getDownloadUrl` endpoint), if that API is proxying or reflecting user-controlled inputs (or is vulnerable to manipulation), it can lead to SSRF. This is specifically dangerous with `follow_redirects=True`, allowing an attacker to bypass initial URL checks or force the bot to access internal network services or cloud metadata endpoints.
**Prevention:** Always validate URLs against SSRF using `validate_url_target` (to check the parsed scheme and domain) before making HTTP requests. Additionally, when using `httpx.AsyncClient` or similar with redirects enabled, inject a request event hook (`event_hooks={"request": [_verify_request]}`) to validate the target URL at every step of a redirect chain, ensuring `validate_resolved_url` is used to prevent DNS rebinding or redirect-based SSRF.

## 2026-04-01 - Command Path Extraction Bypass in ExecTool

**Vulnerability:** Shell brace and bracket expansion operators like `{` and `}` (e.g., in `cat {/etc/passwd,/etc/shadow}`) were not recognized as path boundaries in `_PATH_TRAVERSAL_RE`, `_WIN_PATH_RE`, `_POSIX_PATH_RE`, and `_HOME_PATH_RE`. This allowed attackers to use shell expansions to hide absolute paths from the extraction regex, bypassing the `restrict_to_workspace` validation and enabling a Sandbox Escape.
**Learning:** Shells provide powerful syntax shortcuts like brace expansions (`{,}`) and bracket expansions (`[,]`) which, if not treated as boundaries by validation regexes, can construct valid file paths at runtime while remaining invisible to static string analysis. The lightweight agent tool architecture relies entirely on extracting paths from the raw command string, making robust regex boundaries critical.
**Prevention:** When extracting absolute paths from raw shell commands for security validation (e.g., to enforce `restrict_to_workspace`), ensure regex boundaries use a comprehensive character class like `[\s|<>&;\(\)'"=\`,\[\]\{\}]` to account for paths immediately following shell operators (like `<`, `>`, `&`, `;`, `|`, `(`, `)`), assignment operators (`=`), backticks (`` ` ``), and shell brace/bracket expansions (like `{/etc/passwd,/etc/shadow}`) without spaces. This prevents path traversal and command injection bypasses.

## 2026-04-09 - Prevent SSRF via Redirects in `aiohttp`

**Vulnerability:** The QQ channel used `aiohttp` with `allow_redirects=True` to fetch user-provided media URLs. Since `aiohttp` silently follows HTTP redirects (e.g., 301, 302) without offering an event hook to validate the intermediate or final destination URLs, an attacker could bypass initial URL validation (e.g., passing a valid public URL) and redirect the fetcher to a private/internal network resource, resulting in Server-Side Request Forgery (SSRF).
**Learning:** `aiohttp` lacks the built-in `event_hooks` supported by `httpx` for automatically verifying redirect loops. The `validate_url_target` function only checked the initially provided URL before fetching, and any redirects triggered were blindly trusted by `aiohttp`, breaking the SSRF boundaries designed to protect the internal architecture.
**Prevention:** To prevent SSRF-via-redirects with `aiohttp` in TARS, disable automatic redirects (`allow_redirects=False`) and manually execute a loop for 3xx responses. Resolve the `Location` header correctly using `urllib.parse.urljoin`, then validate each newly resolved URL explicitly with `validate_resolved_url` before issuing the next fetch.
